# Why packaging adds more files than PR #539

The original "9 files versus 2" question compared an early development proposal
with a copied script. It is not a current inventory: the public `main` tree
has no `tests/` directory or `.github/workflows/ci.yml`.
Those test and CI files are discussed below as historical proposed additions.

The end-to-end context is in the [CoreOS artifact lockfile walkthrough](../coreos-assembler/artifact-lockfile-update-flow.md), with a [flowchart](../coreos-assembler/auto-lockfile-updates/coreos-assembler-artifact-lockfile-update-flow.png).

## What PR #539 was

[PR #539](https://github.com/konflux-ci/mintmaker-renovate-image/pull/539) to `mintmaker-renovate-image` changed exactly two files:

1. **`update_artifacts_lockfile`** - a copy of the Python script from `coreos-assembler`
2. **`Dockerfile`** - two new lines to copy the script in and install its dependencies (`pip install ruamel.yaml requests`)

That's it. The idea was: "the script already exists in cosa, let's just drop it into the image."

The maintainer (`staticf0x`) closed it without merging and [requested a separately maintained tool](https://github.com/konflux-ci/mintmaker-renovate-image/pull/539#issuecomment-5231459025):

> This needs to be a tool maintained in a separate repo, perhaps under the konflux-ci org, with its own `pyproject.toml` and specified dependencies and then installed in the image using `pipx` like we do with `rpm-lockfile-prototype` and `refresh-rpm-lockfiles`. We will not maintain the script in this repo.

The separate [`update-artifacts-lockfile` repository](https://github.com/konflux-ci/update-artifacts-lockfile) is the replacement. The current image Dockerfile installs its versioned package with pipx rather than copying the script.

## Why does the new repo need so many files?

Think of it this way. PR #539 was like handing someone a single loose Python file and saying "just run this." The maintainer said: "no, we need it packaged properly - like a real tool you install, not a script you copy around."

Here are the roles of the packaging files and the extra checks described in
the early proposal. Packaging does not require a fixed file count.

---

### `src/update_artifacts_lockfile/__init__.py`

This **is** the tool's logic, originally extracted from the cosa script. The current implementation has also evolved, including the Renovate JSON data-file mode. It lives under `src/` to separate importable package code from project-level files.

`__init__.py` makes this a regular Python package and contains its implementation. Namespace packages can be importable without an `__init__.py`; that is a different packaging pattern.

---

### `pyproject.toml`

This is the file that turns the script into an installable tool.

Without it, someone who wants to run `update_artifacts_lockfile` has to:
1. Download the script manually
2. Manually install `ruamel.yaml` and `requests`
3. Run it with `python script.py`

With it, someone just runs:
```bash
pipx install git+https://github.com/konflux-ci/update-artifacts-lockfile.git@v0.2.0
```
The installer builds a wheel using the backend in `pyproject.toml`, installs its declared runtime dependencies, and exposes `update_artifacts_lockfile` through pipx's bin directory. That directory must be on `PATH`.

The `[project.scripts]` section in `pyproject.toml` is the magic:
```toml
[project.scripts]
update_artifacts_lockfile = "update_artifacts_lockfile:main"
```
This says: "when someone types `update_artifacts_lockfile` in a terminal, call the `main()` function inside the package."

This is what the mintmaker-renovate-image Dockerfile now installs instead of embedding the script from PR #539.

---

### `uv.lock`

A dependency-resolution lockfile used by uv project commands such as
`uv sync --locked` and `uv run --locked`. It records versions and environment
markers rather than simply recording what happened to be installed locally.
Python/platform markers can select different locked dependencies.

**pip and pipx do not read `uv.lock` when installing this package.** A pipx
installation resolves dependencies from package metadata within its constraints;
the pinned Git tag does not pin all transitive dependencies. Using a uv-backed
pipx installer does not turn installation into a lockfile-based project sync.

You do not edit this file by hand. `uv` manages it automatically.

---

### Proposed `tests/__init__.py` and `tests/test_update_artifacts_lockfile.py`

The historical development proposal described eight tests covering situations
such as these. This is not a claim that current upstream contains eight tests:
- Updates a stale checksum
- Skips if the checksum is already correct
- Prints a clean error if the YAML file is missing (instead of crashing)
- Prints a clean error if the YAML file is empty
- Prints an error if a download fails (404)
- Warns and skips if an artifact has no `download_url`
- Warns and skips if an artifact has a malformed checksum

The proposed empty `tests/__init__.py` made the tests a regular package. It is not required merely to import the installed application package.

The proposed tests used `responses` to intercept HTTP requests and return fake responses, allowing checksum and error-handling checks without downloading real artifacts.

---

### Proposed `.github/workflows/ci.yml`

The historical workflow proposal would have run three checks on pull requests:

1. **pytest** - runs the 8 tests on Python 3.12 and 3.13
2. **ruff** - checks that the code follows style rules (like a spell checker, but for code formatting)
3. **mypy** - checks that the type annotations are correct (catches bugs like passing a string where an integer is expected)

This workflow is absent from the current public tree. Its absence alone does
not establish what external CI, review, or branch-protection checks are used.

---

### `.python-version`

Records the project's preferred Python version for uv. This is separate from
`requires-python` in `pyproject.toml`, which declares supported versions; it
does not force pipx to use that interpreter.

---

### `.gitignore`

Tells git which files to ignore - things like `__pycache__/`, `.venv/`, `dist/`. Without it, running tests or building the package would litter the repo with generated files that do not belong in version control.

---

### `README.md`

Explains the lockfile format, usage, installation, and Renovate integration.
The current tree also has `SECURITY.md` for reporting security issues.

## Example integration chain

This illustrates the successful checksum-refresh path; download or input errors
still need to be checked in the command's output.

```
renovate.json (coreos-assembler)
  └─ postUpgradeTasks: 'update_artifacts_lockfile -f "$RENOVATE_POST_UPGRADE_COMMAND_DATA_FILE"'
                              │
              MintMaker matches the configured allowedCommands rule
                              │
              runs inside mintmaker-renovate-image
              where the tool is installed via:
              pipx install git+https://github.com/konflux-ci/update-artifacts-lockfile.git@v0.2.0
                              │
              installer builds a wheel from pyproject.toml
              resolves ruamel.yaml + requests from package metadata (not uv.lock)
              creates `update_artifacts_lockfile` command
                              │
              command reads packageFile paths from Renovate's JSON data file
              command runs __init__.py:main(), downloads artifacts, recomputes the declared hash
              writes updated artifacts.lock.yaml
                              │
              Renovate stages the file → PR has correct checksums ✓
```

---

## Summary

PR #539: two changed files, closed because maintainers wanted an independently maintained, packaged tool instead of an embedded script.

The extra files separate implementation, package metadata, environment locking,
and documentation. Tests and CI are useful additional safeguards, not a magic
file-count requirement. pipx can install a versioned release, but that install
does not automatically use the project's uv lockfile.
